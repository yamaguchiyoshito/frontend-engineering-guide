# 評価の下書き（個人の習熟度・チームチェック）

リポジトリから機械的に集められる事実を根拠に、本ガイドの2つの評価の「下書き」を作ります。下書きは仮説です。確定した評価は、対象者との面談やチームのレビューで根拠を確認してから、本ガイドの記録書式（個人の習熟度評価記録、チームの確認記録）へ転記します。

## 前提と限界

- **リポジトリは変更しない。** 読み取りだけを行い、出力は対象リポジトリの外（または利用者が指定した場所）に書く。ネットワークへのアクセスも行わない。
- **見えるものしか評価しない。** Lv0〜Lv2は成果物（ファイル、コミット、テスト、設定）から見立てられることが多い。Lv3（複数案の比較、原因分析、他者のレビュー）とLv4（チームで再現できる仕組みと、その改善効果の実測）は、PRの議論、レビューコメント、運用実績、利用者の反応といったリポジトリ外の事実が要るため、原則として「候補」に留め、確認事項を付ける。
- **根拠のない判定は書かない。** 根拠が足りない要素技術は「未評価」、チームチェックの項目は「未回答」とし、何を確認すれば判定できるかを書く。未評価とLv0は別物で、Lv0は「試した結果できなかった」判定にのみ使う。
- **個人情報に配慮する。** 出力には対象者の氏名（Git上の表示名）だけを使い、メールアドレスは書かない。評価は本人と評価者が確認する前提の下書きであり、人事評価そのものではない。

## 手順

### 1. 入力を確認する

| 入力 | 必須 | 既定 |
| :--- | :--- | :--- |
| 対象リポジトリのパス | 必須 | なし。相対パスは絶対パスに直す |
| 個人評価の対象者（Gitの表示名またはメールの一部） | 個人評価を作るなら必須 | 未指定なら手順2の結果から作者一覧を示し、利用者に選んでもらう。利用者が選べない状況（自律実行）では、期間内のコミット数が最多の作者を対象にし、その旨を出力に明記する |
| 期間 | 任意 | 全期間。履歴が長い場合は直近12か月を提案する |
| 出力先 | 任意 | 現在の作業ディレクトリの `assessment-draft/<リポジトリ名>/` |

個人評価とチームチェックのどちらか一方だけを求められたら、その一方だけを作る。

### 2. 根拠を集める

同梱のスクリプトを実行する。Python 3.9以降とgitがあれば動き、追加の依存はない。

```bash
python3 <このスキルのディレクトリ>/scripts/collect_evidence.py <リポジトリ> \
  --author "<表示名またはメールの一部>" [--since YYYY-MM-DD] [--until YYYY-MM-DD] --out <出力先>
```

`--since`／`--until` は省略すると全期間。`--bulk-threshold`（既定 30）以上のファイルに触れたコミットは一括コミットとして要素技術ごとの集計から外れ、別枠で報告される。

`evidence.md`（人が読む要約）と `evidence.json`（同じ内容の構造化データ）が出力される。内容は次のとおり。

- 技術スタック、設定ファイル、CIの定義とその中の検査（lint、型検査、テスト、E2E、SAST、監査、デプロイ）
- テスト・Storybook・E2Eのファイル数、ソースコードの内容から拾った手がかり（Server Components、ARIA属性、Zod、フォーム、キャッシュ制御など）と、その例となるファイル
- 機密情報らしき文字列の有無（場所のみ。値は出さない）
- Git履歴：作者ごとの件数と期間、月ごとの件数、マージ・PRの慣行、コミットメッセージの規約、revert、タグ
- 対象者の活動：触れたファイルの数、要素技術ごとの手がかり（触れたファイル数、コミット例、内容の手がかり）、マージ・レビューの痕跡、一括コミットと取り込み役の注意、現在のツリーに無いファイルの数
- チームチェックの小テーマごとに整理した事実

`evidence.md` の手がかりは「見に行く場所」であって根拠そのものではない。パスやライブラリ名の一致で拾っているため、文書やサンプルが誤って拾われることがある。判定に使う箇所は実際のファイルやコミット（`git -C <repo> show <hash> --stat`）を開いて確かめ、根拠には必ずパスまたはコミットの短縮ハッシュを書く。スクリプトは現在のツリーだけを走査するので、削除・移動されたファイルの中身は見えない（必要なら `git -C <repo> log --diff-filter=D --name-only --author=<名前>` で確認する）。

### 3. 個人の習熟度の下書きを作る

`references/skills.json` に31の要素技術の定義（Lv0〜Lv4の到達状態、評価対象・前提、はじめの一歩）がある。`references/skill-evidence-map.md` に、要素技術ごとに「どの手がかりが何を示すか」「リポジトリからは判定できないこと」をまとめている。要素技術ごとに次を決める。

0. まず対象者の活動の「注意」を読む。一括コミット（初期インポート、一括移行、整形）に含まれるファイルは、その要素技術の根拠に数えない。非マージコミットがほとんど無くマージだけが多い作者は取り込み・レビュー役であり、`git.collaboration` の根拠にはなるが他の要素技術の根拠にはならない。どちらも確認事項として「その成果物を本人が書いたか」を残す。
1. 手がかりが無い、または対象者が触れていない → **未評価**。確認事項に「担当した成果物があるか」を書く。
2. 例に沿った変更やテンプレート的な追加が中心、設定や例外処理は他者の変更に依存 → **Lv1** の候補。
3. 要件が明確な機能を、実装・検証（テスト）・修正まで一人で完結させたコミット群がある → **Lv2** の候補。
4. 設計判断の痕跡（複数案の比較、原因分析、構成の段階的な改善、他者のレビュー）があれば **Lv3 の候補**として挙げるが、確認事項に「PRの議論やレビューで判断の根拠を確認する」と書く。
5. 共通部品、規約、自動検査、教材を整備し、他者が使っている痕跡があれば **Lv4 の候補**。ただし利用実績と改善効果の実測はリポジトリ外にあるため、必ず確認事項を付ける。

各要素技術の出力は、Lvと到達状態の定義文（`skills.json` の文面をそのまま）、根拠（3件以内。パスまたはハッシュ付き）、確認事項（1〜2件）の3つで構成する。

### 4. チームチェックの下書きを作る

`references/checklist-items.json` に100項目（小テーマ、観点、項目文、アンチパターンかどうか、原文の参照先）がある。`references/team-evidence-map.md` に小テーマごとの手がかりをまとめている。項目ごとに次を決める。

- 項目文が求める状態を示す事実がある → **はい**。一部にとどまる、導入したが止まっている、対象範囲が限定的 → **はい、でも…**。
- 求める状態が無いことを示す事実がある → **いいえ**。着手の痕跡がある → **いいえ、でも…**。
- 研修、定期的な振り返り、計測結果の活用、役割分担、事業側との連携のように、リポジトリに痕跡が残りにくいもの → **未回答**。評価記述に、何を誰に確認すれば判定できるかを書く。
- 項目の前提となる対象（バックエンド、API、外部ツール、本番運用）がそのリポジトリに存在しない → **該当なし**。配点の対象から外し、評価記述に理由と、本来の評価対象が別リポジトリにあるかを書く。前提が無いために自明に満たされる項目（例：バックエンドが無いので「バックエンドに依存せず開発できる」、Dependabot が無いので「放置された更新PRが無い」）も「はい」「いいえ」ではなく該当なしにする。小さなリポジトリで得点が水増しされるのを防ぐためである。
- **各小テーマの4番目はアンチパターン。** 項目文は「望ましくない状態」を述べており、望ましい状態の答えは「いいえ」で、配点が逆転する（いいえ 1点、はい 0点）。例：機密情報のハードコーディングが見つからなければ「いいえ」。

配点は出典（日本CTO協会「Webフロントエンド版DX Criteria」使い方）に従い、はい 1点、「でも…」0.5点、いいえ 0点。小テーマ4点、大テーマ20点、全体100点。未回答は0点として集計し、回答数を併記する。該当なしは分母からも外し、「得点 x / 100（該当なし n 件を除くと x / (100 − n)）」の形で両方を書く。

評価記述には、実態（何がどこにあるか）、対象範囲、頻度、根拠資料（パス）を1〜3文で書く。望ましい回答例の文体に合わせるが、実在しない取り組みを書かない。

### 5. 出力する

`references/output-format.md` の書式どおりに、次の4ファイルを出力先へ書く。

| ファイル | 内容 |
| :--- | :--- |
| `individual-draft.md` | 個人の習熟度の下書き（領域ごと、要素技術ごとにLv＋定義文、根拠、確認事項）。先頭に対象者、期間、集計、注意書き |
| `individual-draft.json` | 本ガイドの習熟度マトリクスと同じ形（`levels`：要素技術ID → 0〜4）。候補止まりのLv3・Lv4は含めず `candidates` に分ける |
| `team-draft.md` | チームチェックの下書き（大テーマ・小テーマごとの得点と回答数、項目ごとに回答、項目文、評価記述、根拠） |
| `team-draft.json` | 本ガイドのチームチェックと同じ形（`items`：項目ID → `answer`（yes／yes-but／no-but／no／na）と `note`）。`na` は該当なしで、本ガイドのページには取り込まれない |

最後に、利用者への報告として、対象と期間、個人評価の分布（未評価／Lv候補の件数）、チームチェックの得点と回答数、確認事項の上位5件、下書きの位置づけ（面談・レビューで確認してから記録書式へ転記）を短くまとめる。

## 判定で迷ったとき

- 手がかりが「ライブラリを導入している」だけなら、使いこなしの判定はできない。導入は要素技術のLv1の根拠にはなるが、Lv2以上の根拠にはならない。
- 他者が書いたコードの軽微な修正（typo、定数の変更）は、その要素技術の根拠に数えない。
- 生成されたコード（lockfile、ビルド成果物、スナップショット、`generated` ディレクトリ）は根拠から除く。
- 初期インポートや一括移行のような巨大なコミット（数十ファイル以上）は、含まれる要素技術すべての根拠にはしない。そのコードを本人が書いたかは、その後の個別の変更や面談で確認する。
- マージコミットだけが多い作者は、レビューや取り込みの役割を担っている可能性が高い。`git.collaboration` の根拠にはなるが、他の要素技術の根拠には数えない。
- モノレポでは対象者が関わるパッケージを特定し、評価の対象範囲として明記する。
- フロントエンド以外のリポジトリでは、該当する要素技術だけを評価し、残りは未評価とする。チームチェックは適用可否を評価記述に書く。
