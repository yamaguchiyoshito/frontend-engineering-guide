# チームチェックの小テーマごとの手がかり

`collect_evidence.py` の出力（`team` セクション：小テーマごとの事実、`ci`、`configs`、`tests`、`signals`、`secrets`、`git`）を回答に読み替えるための対応表。各小テーマは「メトリクスの計測」「学習と改善」「プラクティス」「アンチパターン」の4観点で構成され、4番目のアンチパターンは望ましい状態の答えが「いいえ」で配点が逆転する。

リポジトリの事実で判定できるのは主に「プラクティス」と「アンチパターン」で、「メトリクスの計測」と「学習と改善」の多くは、計測の運用や研修・振り返りの実施というリポジトリ外の事実が要る。これらは、ダッシュボード設定や計測スクリプト、`docs/` の議事録・ADR のような痕跡がない限り未回答とし、確認先を評価記述に書く。

| 小テーマ | リポジトリで見える手がかり | 判定の目安 |
| :--- | :--- | :--- |
| 1-1 コードベース | 型付け言語（`tsconfig` と `strict`）、ESLint／Prettier、CI の lint／typecheck、`console.log`／`any`／`@ts-ignore`／`eslint-disable` の多さ、依存の更新頻度（lockfile の変更履歴）、PR のサイズとリードタイム | 1-1-2 はツールの導入と CI 実行で「はい」。1-1-1 は指標の集計の痕跡がなければ未回答。アンチパターンは放置された警告や巨大PRの常態化が見えれば「はい」 |
| 1-2 開発環境 | `.nvmrc`／`engines`、lockfile、`README` のセットアップ手順、Dev Container／Docker、`.env.example`、起動スクリプト | 手順と再現性の整備があれば「はい」。手順が README に無い、個人環境依存の記述があれば「いいえ、でも…」 |
| 1-3 UIコンポーネント | コンポーネント指向のフレームワーク、`components/` の構成、Storybook、デザイントークン、UI部品ライブラリ | 部品化と単独表示（Storybook）で「はい」。画面直書きが中心なら「いいえ、でも…」 |
| 1-4 アプリケーション設計 | ディレクトリ構成（機能別・レイヤー別）、状態管理の方針、API層の分離、ADR／設計文書 | 分離が一貫していれば「はい」。設計文書が無ければ学習と改善は未回答 |
| 1-5 技術選定 | ADR、`docs/` の選定記録、依存の数と重複（同目的のライブラリの併存）、非推奨パッケージ | 記録があれば「はい」。併存・非推奨が多ければアンチパターン側 |
| 2-1 パフォーマンス | Lighthouse CI、`web-vitals`、バンドル分析、`next/image`、動的インポート、キャッシュ制御、性能予算 | 計測の仕組みがあれば 2-1-1「はい」。最適化の実装があればプラクティス「はい」 |
| 2-2 アクセシビリティ | `eslint-plugin-jsx-a11y`、`vitest-axe`／`jest-axe`、Storybook a11y addon、`aria-*`／`alt`／`lang`、キーボード操作のテスト | 自動検査が CI にあれば「はい」。属性の利用だけなら「はい、でも…」 |
| 2-3 セキュリティ | SAST（CodeQL、Semgrep）、`npm audit`／`pnpm audit`／Trivy／Snyk の CI 実行、Dependabot／Renovate、`SECURITY.md`、CSP、`dangerouslySetInnerHTML` とサニタイズ、機密情報の検出結果 | 2-3-1 は SAST が PR ごとに動けば「はい」。2-3-3 は更新検知の設定で「はい」。2-3-4 は `secrets` の検出が 0 件なら「いいえ」（1点）、検出があれば「はい」（0点） |
| 2-4 プライバシー | 解析ツールの同意管理、個人情報の扱いの文書、ログのマスキング、Cookie の属性、プライバシーポリシーへの参照 | 文書と実装の両方がなければ未回答か「いいえ、でも…」 |
| 2-5 デザイン | デザイントークン、Figma との同期（Style Dictionary 等）、Storybook、UI の規約文書 | 共通テーマで実装されていれば「はい」 |
| 3-1 テスト | ユニット／コンポーネント／結合／E2E のファイル数、CI での実行、カバレッジ設定、MSW、テスト方針の文書 | CI でテストが PR ごとに動けば「はい」。E2E が無ければ該当項目は「いいえ、でも…」 |
| 3-2 ビルド | ビルドの CI 実行、キャッシュ、ビルド時間の計測、再現性（lockfile、固定バージョン）、環境別ビルド | CI ビルドと lockfile があれば「はい」 |
| 3-3 デプロイ | デプロイ定義（Vercel／Netlify／Pages／Docker／k8s）、環境（staging／production）、ロールバック手順、リリースタグ、`environment:` | 自動デプロイがあれば「はい」。手順書やロールバックが無ければ「はい、でも…」 |
| 3-4 サプライチェーン | Dependabot／Renovate、lockfile、監査の CI、依存の更新頻度、固定バージョン、SBOM | 更新検知と監査があれば「はい」 |
| 3-5 CI/CD | ワークフローの有無と内容、`pull_request` トリガー、必須検査、並列化、所要時間、`concurrency` | PR ごとに lint／test／build が動けば「はい」。失敗が常態化（revert の多さ、`continue-on-error`）ならアンチパターン側 |
| 4-1 サーバー | BFF／API 層の分離、Server Components／Server Actions の使い方、認証の扱い、OpenAPI の利用 | API 層の分離と型生成があれば「はい」 |
| 4-2 インフラ | IaC（Terraform、CDK）、環境変数の管理（`.env.example`）、CDN／エッジの設定、Dockerfile | 定義がリポジトリにあれば「はい」。無ければ別リポジトリの可能性を確認 |
| 4-3 キャッシュ | `Cache-Control`／`stale-while-revalidate`、`revalidate*`、Service Worker、CDN 設定、TanStack Query の `staleTime` | 方針が設定に表れていれば「はい」 |
| 4-4 モニタリング | Sentry／Datadog 等の導入、`web-vitals` の送信、ログの設計、アラート設定 | 導入と設定があれば「はい」。アラートや対応の運用は未回答 |
| 4-5 障害対応 | インシデント手順書（`docs/`、`RUNBOOK`）、ロールバック、`revert` の履歴、ポストモーテム | 手順書が無ければ未回答か「いいえ、でも…」 |
| 5-1 専門性の育成 | `docs/` の学習資料、オンボーディング文書、ADR、ペア作業の痕跡（`Co-authored-by`） | 多くは未回答。文書があれば「はい、でも…」 |
| 5-2 イネーブリング | 共通部品・テンプレート・ジェネレータ、CLI、他チームが使う設定の整備 | 共通化の痕跡があれば「はい、でも…」 |
| 5-3 職務定義 | CODEOWNERS、役割の記述、`CONTRIBUTING.md` | 文書があれば「はい、でも…」。無ければ未回答 |
| 5-4 ビジネス連携 | イシュー・PR のテンプレートに目的や指標の欄、`docs/` の要件・KPI | 多くは未回答 |
| 5-5 外部発信 | 公開リポジトリ、`README` の充実、ブログ・登壇への参照、OSS への貢献 | 多くは未回答か「いいえ、でも…」 |

## 回答の書き方

- 「はい」は、項目文が求める状態が対象範囲（このリポジトリ）で満たされている事実を書く。「はい、でも…」は、満たす部分と不足（対象範囲、頻度、停止中）を書く。
- 「いいえ」は、無いことを示す事実（設定が存在しない、CI に含まれない）を書く。「いいえ、でも…」は、着手の痕跡（イシュー、未使用の設定、一部のパッケージだけ）を書く。
- 未回答は、何を誰に確認すれば判定できるかを書く（例：「計測の有無と頻度を開発責任者に確認」「研修の実施記録を確認」）。
- アンチパターンの項目文は望ましくない状態なので、「その状態が無い」ことを示す事実があれば「いいえ」（1点）、見つかれば「はい」（0点）。「一部にある」は「はい、でも…」か「いいえ、でも…」（いずれも 0.5点）。
