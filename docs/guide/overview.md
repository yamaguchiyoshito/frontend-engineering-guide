# ガイドの目的と評価の全体像

フロントエンド開発の品質と生産性を高めるには、担当者が何を実行できるかに加え、その能力を発揮できる開発環境と運用が必要です。本書では、個人の習熟度とチームの取り組みを共通の基準で確認し、育成・担当配置・開発環境の整備・業務改善につなげます。

本書を使うと、次の三つを整理できます。

1. 担当業務に必要な要素技術と、現在実行できる範囲。
2. チームとして実施できている取り組みと、不足している仕組み。
3. 次に取り組む改善、その担当者、完了条件、効果を確認する方法。

個人の評価には、28の要素技術それぞれのLv0〜Lv4を使用します。チームの確認には、100項目のチェックリストを使用します。両者は関連しますが、評価対象と判定方法が異なるため、単一の点数へ換算しません。

## 対象読者

| 読者 | 本書を使って行うこと |
| :--- | :--- |
| 開発メンバー | 自分の実行可能な範囲と根拠を整理し、次に習得する内容を決めます。 |
| テックリード・レビュー担当者 | 共通の基準で習熟度を確認し、設計・実装・検証の支援範囲を決めます。 |
| プロジェクト責任者・チームリーダー | 必要な要素技術に習熟した担当者と代替要員を確保し、環境・運用の改善を計画します。 |
| 横断支援・育成担当者 | 複数チームに共通する課題を把握し、標準、共通部品、教材、支援体制を整備します。 |

## 三つの概念を区別する

| 概念 | 何を表すか | 表記 | 例 |
| :--- | :--- | :--- | :--- |
| 領域 | 扱う技術や作業のまとまり | 4つの領域名 | React実装は「フレームワーク・実装領域」に分類します。 |
| 習熟度 | 個人が、その要素技術でどこまで実行できるか | Lv0〜Lv4、未評価 | React実装を支援の下で行える場合は、基準と証拠を確認してLv1と判定します。 |
| チームの取り組み | 対象チーム・環境で、必要な仕組みが運用されているか | 達成・一部達成・未達・未評価・対象外 | CIで必須検査を実行し、失敗した変更をマージできない設定にしているかを確認します。 |

領域は扱う技術や作業の分類を示し、習熟度のLv0〜Lv4は、その要素技術で実行できる範囲を示します。同じ領域に含まれる要素技術でも、個人の習熟度はそれぞれ異なります。例えば、GitはLv3、JavaScriptはLv2という状態があります。

本書とチェック項目の原文にあるPRはPull Requestを指します。GitLabを使用する場合は、MR（Merge Request）と読み替えてください。

## 領域

| 領域 | 内容 | 要素技術数 |
| :--- | :--- | :---: |
| 基礎領域 | Web、HTML、CSS、JavaScript、Gitの基礎 | 5 |
| 応用基礎領域 | 意味構造、レスポンシブ、DOM、非同期、TypeScript、アクセシビリティ、SEO、チーム開発 | 8 |
| フレームワーク・実装領域 | React、コンポーネント設計、状態管理、フォーム、API連携、入力検証、Storybook | 7 |
| 品質・高度化領域 | 各種テスト、テスト設計、性能、セキュリティ、品質保証 | 8 |

各領域の要素技術は、担当業務と前提知識に応じて組み合わせて学習します。必要な基礎を確認しながらReactの実装へ進み、テスト設計やセキュリティも並行して学習できます。

## 個人の能力とチームの条件を分けて確認する

例えば、あるメンバーが型検査を設定・実行できても、チームのCIにその検査が組み込まれていなければ、チームの品質確保には不足が残ります。一方、CIが整っていても、各メンバーがその設定を理解し、改善できるとは限りません。

評価では、次の問いを分けて確認します。

- **個人について：** 本人は、どの条件の下で、何を説明・実装・検証・改善できますか。
- **チームについて：** その取り組みは、どのリポジトリ・環境・期間で、誰が継続して運用していますか。

CIの管理権限、検証環境、担当機会などがない場合は、その制約を記録します。制約だけを理由に個人のLvを下げず、演習や過去の成果物で確認するか、未評価とします。

また、28の要素技術はフロントエンド領域の評価項目です。[チームチェックリスト](../checklists/index.md)に含まれるバックエンド、インフラ、プライバシー、事業部門との連携などは、関係する専門担当者と共同で確認します。これらの能力全体を28の要素技術だけで評価するものではありません。
