# 障害対応

**大テーマ：** 4. 効果的なシステム設計  
**小テーマ：** 4-5 障害対応

**前提となる用語：** [インシデントとポストモーテム](../guide/glossary.md#インシデントとポストモーテム)、[ロールバック](../guide/glossary.md#ロールバック)、[モニタリングとオブザーバビリティ](../guide/glossary.md#モニタリングとオブザーバビリティ)、[SLO](../guide/glossary.md#slo)

## 4-5-1：メトリクスの計測

ログインの失敗など障害に繋がる主要なユーザーアクションに関する利用状況データを計測している。

::: example
ログイン、検索、登録、送信、決済など、サービスで重要な操作の実行数・成功率・失敗理由を計測しています。正常な入力エラーとシステム障害を区別し、利用者の操作が完了できない状態を検知できます。必要な範囲でデータを収集し、異常時の調査と改善の優先順位付けに利用しています。
:::

[原文の参照先](https://dxcriteria.cto-a.org/80247739886549a6a8a11dfb1ce65fb5)

## 4-5-2：学習と改善

障害後、Webフロントエンドを主とする開発者も漏れなく当事者としてポストモーテムに参加している。

**補足**

障害発生後のポストモーテムにも学びの場を活かせるようにしていることも重要

::: example
障害後の振り返りには、フロントエンド開発者を含む関係者が当事者として参加しています。利用者への影響、画面上の症状、検知・連絡・復旧の経緯を共有し、原因と改善策を共同で整理しています。個人への責任追及を避け、改善項目の担当者・期限・完了確認を記録しています。
:::

[原文の参照先](https://dxcriteria.cto-a.org/cba508f6da494a06a5192f5ebc4625df)

## 4-5-3：プラクティス

Webフロントエンドを主とする開発者にも障害対応のロールと責任を明確にしている。

::: example
フロントエンド開発者の障害対応上の役割を明文化しています。画面側の切り分け、影響範囲の確認、利用者向け表示の修正、機能停止や切り戻しの支援などについて担当と判断権限を定めています。連絡網、手順、必要なアクセス権を共有し、訓練で実行できることを確認しています。
:::

[原文の参照先](https://dxcriteria.cto-a.org/26f2c26ef4cc4a22b9cc9b284e4cc577)

## 4-5-4：アンチパターン

障害対応に必要なスキルや知識の獲得にチームや組織として取り組んでおらず、業務負荷が一部の個人に集中してしまっている。

::: example
障害対応に必要な知識を手順書と事例集にまとめ、ペア対応、当番の交代、定期的な訓練で複数名が対応できる状態を維持しています。対応履歴と負荷を月次で確認し、特定の個人に偏る場合は役割と育成計画を見直しています。不在時の代替担当者も明確にしています。
:::

[原文の参照先](https://dxcriteria.cto-a.org/8315b91196f3469a999f9b8c130d6e14)
