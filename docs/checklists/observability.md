## 4-4-1：メトリクスの計測

SLI/SLOに関わるシステムの稼働を24時間365日モニタリングしている。

**補足**

下記の方法を例示する。

- ヘルスチェック用のエンドポイントを設け、ステータス確認ができるようになっている
- プロセスの監視
- ログのモニタリング
- アラートの通知
- トラフィック分析 (DDoS や 不正アクセス数の検知)

::: example
主要サービスのSLIを定義し、可用性、応答時間、エラー率などを24時間365日、自動で監視しています。SLOの評価期間・目標値・対象範囲を明記し、目標からの逸脱や急激な悪化を検知できます。監視停止も検出し、サービスの対応時間帯と重要度に応じた通知先を設定しています。
:::

[原文の参照先](https://dxcriteria.cto-a.org/197aa2a71774476a80eaeef043dadb1b)

## 4-4-2：学習と改善

エラーログを収集し、定期的（月ごと〜半年ごと）にエラーの傾向を分析し、その結果をもとに改善活動を計画している。

::: example
フロントエンド、バックエンド、インフラのエラーログを収集し、月次で発生件数、影響する利用者、再発状況、リリースとの関係を分析しています。影響と頻度から改善対象を選び、担当者・期限・完了条件を設定しています。対策後は発生傾向を比較し、再発の有無を確認しています。
:::

[原文の参照先](https://dxcriteria.cto-a.org/a96a63a4179c4a319c39301411d1274c)

## 4-4-3：プラクティス

各種事象を調査する際にバックエンド、インフラ、フロントエンドに渡って統合されたログをトレースできるようになっている。

::: example
画面操作からAPI、バックエンド処理、インフラの記録まで、リクエストIDやトレースIDで関連付けて調査できます。ログの時刻と環境・バージョンの情報を統一し、検索手順と閲覧権限を整備しています。機密情報を不要に記録せず、代表的な障害を使って追跡できることを確認しています。
:::

[原文の参照先](https://dxcriteria.cto-a.org/9dd3fd228f6240d184ef6679c88a2b88)

## 4-4-4：アンチパターン

モニタリングにおける異常検知時のアラートが設定されていなかったり、対応フローが確立しておらず問題が解決されなかったりしている。

**補足**

例えばSentryを導入したものの、アラートを通知するように設定されていないなどのケースが考えられる。

::: example
異常検知の条件、重大度、通知先、一次対応、エスカレーション、復旧確認までの手順を定めています。通知に応答がない場合の連絡経路も用意しています。定期的な訓練で通知から対応完了までを確認し、担当不明や通知未設定によって問題が放置される状態を防いでいます。
:::

[原文の参照先](https://dxcriteria.cto-a.org/4e236d711c09478392092ad957948336)
